This document provides an exhaustive analysis of each module's internal structure, including every class, method, entity field, endpoint, and design pattern used.

## Module 1: common-lib

**Artifact:** `com.enpay:common-lib`  
**Type:** Non-bootable JAR library (no `spring-boot-maven-plugin`)  
**Package:** `com.enpay.common`  
**Purpose:** Shared constants, DTOs, exceptions, events, and utility classes used by all services.

### 1.1 Constants (`com.enpay.common.constant`)

#### CollectionCategory (Enum)
Categorizes collections for organizational purposes.
- `TRIP` - Travel-related expense group
- `EXPENSE` - General shared expenses
- `OTHER` - Uncategorized

#### CollectionRole (Enum)
Role-based access control within a collection.
- `ADMIN` - Full control: manage members, edit/delete collection, create expenses
- `EDITOR` - Create and edit expenses
- `MEMBER` - Read-only access

#### CollectionStatus (Enum)
Lifecycle status of a collection.
- `ACTIVE` - Open for new expenses and settlements
- `CLOSED` - No further modifications allowed

#### Currency (Enum)
Supported currencies with display metadata.
- `MYR` ("Malaysian Ringgit", "MYR")
- `SGD` ("Singapore Dollar", "SGD")
- `USD` ("United States Dollar", "USD")
- Static constant: `DEFAULT_CODE = "MYR"`

#### InvitationStatus (Enum)
- `PENDING` - Awaiting recipient response
- `ACCEPTED` - Invitation accepted, user joined collection
- `DECLINED` - Invitation rejected

#### SplitType (Enum)
Bill-splitting strategy types.
- `EQUAL` - Even distribution among all participants
- `PERCENTAGE` - Custom percentage allocation
- `EXACT` - Fixed amounts per participant
- `HYBRID` - Some participants have fixed amounts, rest split remainder
- `HIERARCHICAL` - Tiered groups (primary/secondary) with different shares

#### TransactionStatus (Enum)
- `PENDING` - Transaction initiated, not yet completed
- `COMPLETED` - Successfully processed
- `FAILED` - Processing failed (compensated)
- `REVERSED` - Previously completed, now reversed

#### TransactionType (Enum)
- `SETTLEMENT` - Single expense share settlement
- `TOP_UP` - Wallet balance top-up
- `TRANSFER` - Direct transfer between users
- `NETTING` - Bilateral netting of multiple debts

### 1.2 DTO (`com.enpay.common.dto`)

#### ApiResponse\<T\>
Generic API response wrapper used by all services.
- `boolean success` - Operation success flag
- `String message` - Human-readable message
- `T data` - Response payload (nullable, excluded when null via `@JsonInclude.NON_NULL`)
- `LocalDateTime timestamp` - ISO formatted timestamp

Static factory methods:
- `success(T data)` - Success with default message
- `success(String message, T data)` - Success with custom message
- `error(String message)` - Error with no data

### 1.3 Events (`com.enpay.common.event`)

#### NotificationEvent
RabbitMQ message payload for async notification delivery.
- `String userId` - Notification recipient
- `String type` - Event category (e.g., "SETTLEMENT_RECEIVED", "EXPENSE_CREATED")
- `String title` - Notification title
- `String message` - Full notification body
- `String referenceId` - Related entity ID for deep linking
- `LocalDateTime timestamp` - Event creation time

#### RabbitMQConstants
Centralized constants for all RabbitMQ infrastructure names.

**Exchange:** `enpay.notifications`

**Queues:**
- `enpay.notifications.settlement`
- `enpay.notifications.expense`
- `enpay.notifications.invitation`

**Routing Key Patterns (for binding):**
- `notification.settlement.#`
- `notification.expense.#`
- `notification.invitation.#`

**Specific Routing Keys (for publishing):**
- `notification.settlement.received`
- `notification.settlement.confirmed`
- `notification.expense.created`
- `notification.expense.reminder`
- `notification.invitation.received`

### 1.4 Exceptions (`com.enpay.common.exception`)

#### BaseException (Abstract)
Base for all custom exceptions. Carries `HttpStatus` for automatic HTTP response mapping.
- Constructor: `(String message, HttpStatus status)`
- Constructor: `(String message, HttpStatus status, Throwable cause)`

#### Concrete Exceptions
| Exception | HTTP Status | Usage |
|---|---|---|
| `BadRequestException` | 400 | Invalid input parameters |
| `UnauthorizedException` | 401 | Invalid credentials, expired tokens |
| `ForbiddenException` | 403 | Insufficient permissions |
| `ResourceNotFoundException` | 404 | Entity not found (3 constructors: by name+id, name+field+value, message) |
| `ConflictException` | 409 | State conflicts |
| `DuplicateResourceException` | 409 | Duplicate entity creation |
| `InsufficientBalanceException` | 422 | Wallet balance too low for operation |

#### GlobalExceptionHandler
`@RestControllerAdvice` that handles:
1. `BaseException` -> Returns appropriate HTTP status with `ApiResponse.error()`
2. `MethodArgumentNotValidException` -> 400 with concatenated field error messages
3. `HttpMessageNotReadableException` -> 400 "Malformed request body"
4. `Exception` (catch-all) -> 500 "An unexpected error occurred" (logged)

### 1.5 Utilities (`com.enpay.common.util`)

#### MoneyUtil
Financial arithmetic utility using `BigDecimal` with precision scale=4 and `HALF_UP` rounding.
- `add(a, b)` - Addition with scale
- `subtract(a, b)` - Subtraction with scale
- `multiply(a, b)` - Multiplication with scale
- `divide(a, b)` - Division with scale
- `roundToScale(value, scale)` - Round to custom scale
- `isPositive(value)` - Check > 0
- `isZeroOrNegative(value)` - Check <= 0
- `isNegative(value)` - Check < 0
- `ZERO` - Pre-scaled zero constant

#### NotificationHelper
Fire-and-forget notification utility that wraps exceptions to prevent notification failures from affecting business transactions.
- `sendFireAndForget(Consumer<Map> sender, userId, type, title, message, referenceId, Logger log)` - Builds notification payload map, calls sender, catches and logs any exception

## Module 4: api-gateway

**Artifact:** `com.enpay:api-gateway`  
**Port:** 8080  
**Package:** `com.enpay.gateway`  
**Purpose:** Spring Cloud Gateway - single entry point for all client requests with JWT authentication and rate limiting.

### 4.1 Application Class
`ApiGatewayApplication` - `@EnableDiscoveryClient`

### 4.2 JwtAuthenticationFilter
Custom `AbstractGatewayFilterFactory` that intercepts every request:

**Open paths (no auth required):**
- `/api/auth/register`
- `/api/auth/login`
- `/api/auth/refresh`

**Logic:**
1. Check if path starts with any open path - skip auth if yes
2. Extract `Authorization: Bearer <token>` header
3. Validate JWT signature and expiration via `JwtUtil`
4. Extract `userId` (subject claim) from token
5. Inject `X-User-Id` header into downstream request
6. On failure: return 401 JSON response `{"success":false,"message":"..."}`

### 4.3 JwtUtil (Gateway)
- `validateToken(String token)` - Verify JWT signature with HMAC-SHA key
- `extractUserId(String token)` - Get subject claim (userId)
- Uses `jjwt` library with `Keys.hmacShaKeyFor()` from configured secret

### 4.4 RateLimiterConfig
Redis-based rate limiting with `KeyResolver`:
- **Primary key:** `X-User-Id` header (authenticated user)
- **Fallback key:** Client IP address (unauthenticated/anonymous)

### 4.5 Gateway Routes (7 routes)
| Route ID | Path Predicate | Target URI | Special Filters |
|---|---|---|---|
| auth-service | `/api/auth/**` | `lb://AUTH-SERVICE` | - |
| wallet-service | `/api/wallets/**` | `lb://WALLET-SERVICE` | - |
| collection-service | `/api/collections/**` | `lb://COLLECTION-SERVICE` | - |
| transaction-service | `/api/transactions/**` | `lb://TRANSACTION-SERVICE` | `RequestRateLimiter` (5 req/s, burst 10) |
| currency-service | `/api/currency/**` | `lb://CURRENCY-SERVICE` | - |
| notification-service | `/api/notifications/**` | `lb://NOTIFICATION-SERVICE` | - |
| reporting-service | `/api/reports/**` | `lb://REPORTING-SERVICE` | - |

### 4.6 CORS Configuration (via config-server)
- Allowed origins: `*`
- Allowed methods: GET, POST, PUT, DELETE, OPTIONS
- Allowed headers: Authorization, Content-Type, X-User-Id
- Exposed headers: Authorization
- Max age: 3600 seconds

### 5.3 DTOs

| DTO | Fields | Validation |
|---|---|---|
| `RegisterRequest` | email, password, firstName, lastName, phone | `@Email`, `@NotBlank`, `@Size(min=8)` for password |
| `LoginRequest` | email, password | `@Email`, `@NotBlank` |
| `RefreshTokenRequest` | refreshToken | `@NotBlank` |
| `AuthResponse` | accessToken, refreshToken, userId, email, firstName, lastName | - |
| `UserResponse` | userId, email, firstName, lastName, status | - |

### 5.4 Service Implementation (AuthServiceImpl)

#### register(RegisterRequest)
1. Check email uniqueness (`existsByUserEmail`) -> throws `DuplicateResourceException`
2. Map `RegisterRequest` to `User` entity via `UserMapper`
3. Save `User` to DB (UUID auto-generated in `@PrePersist`)
4. Create `UserCredential` with BCrypt-encoded password
5. **[Feign]** Call `walletClient.createWallet(userId)` - wrapped in try-catch for graceful degradation
6. Generate JWT access token (with userId + email claims, configurable expiration)
7. Generate JWT refresh token (userId only, 7-day default expiration)
8. Return `AuthResponse`

#### login(LoginRequest)
1. Find user by email -> throws `UnauthorizedException` if not found
2. Find credential by userId -> throws `UnauthorizedException` if not found
3. Verify password with BCrypt `matches()` -> throws `UnauthorizedException` if mismatch
4. Generate new access + refresh tokens
5. Return `AuthResponse`

#### refreshToken(RefreshTokenRequest)
1. Validate refresh token via `JwtUtil.validateToken()` -> throws `UnauthorizedException`
2. Extract userId from token
3. Find user by ID -> throws `ResourceNotFoundException`
4. Generate new access + refresh tokens
5. Return `AuthResponse`

#### getUserById(String userId)
1. Find user by ID -> throws `ResourceNotFoundException`
2. Map to `UserResponse` via `UserMapper`

### 5.5 JWT Configuration

#### JwtConfig (Properties)
- `jwt.secret` - HMAC signing key (256-bit minimum)
- `jwt.expiration` - Access token TTL in ms (default: 86400000 = 24h)
- `jwt.refreshExpiration` - Refresh token TTL in ms (default: 604800000 = 7d)

#### JwtUtil (Auth Service)
- `generateAccessToken(userId, email)` - Creates JWT with subject=userId, claim.email=email
- `generateRefreshToken(userId)` - Creates JWT with subject=userId
- `validateToken(token)` - Verifies signature and expiration
- `extractUserId(token)` / `extractEmail(token)` - Claim extraction

### 5.6 Security Configuration
- **CSRF:** Disabled (stateless API)
- **Session:** `STATELESS`
- **Open endpoints:** `/api/auth/**` (permitAll)
- **All others:** Authenticated (but gateway handles auth, so this is defense-in-depth)
- **PasswordEncoder:** BCryptPasswordEncoder

### 7.2 Bill-Splitting Engine (`com.enpay.collection.engine`)

#### SplitStrategy (Interface)
```java
List<ShareResult> calculate(BigDecimal totalAmount, List<ParticipantShare> participants);
```

#### EqualSplitStrategy
- Divides `totalAmount` equally among all participants
- Uses `RemainderDistributor` to distribute penny-level remainders
- Example: $10.00 / 3 = $3.3334, $3.3333, $3.3333

#### PercentageSplitStrategy
- Each participant specifies a percentage (must sum to 100%)
- Validates total = 100%, throws `BadRequestException` if not
- Uses `RemainderDistributor` for precision

#### ExactSplitStrategy
- Each participant specifies an exact fixed amount
- Validates sum of amounts equals total, throws `BadRequestException` if not

#### HybridSplitStrategy
- Some participants have `fixedAmount`, others don't
- Fixed amounts are assigned first
- Remainder (`total - sum(fixed)`) is split equally among non-fixed participants
- Uses `RemainderDistributor` for the equal split portion

#### HierarchicalSplitStrategy
- Participants have `shareWeight` values defining tiers
- Higher weight = larger share proportionally
- Total is distributed based on weight ratios
- Uses `RemainderDistributor` for precision

#### SplitStrategyFactory
Maps `SplitType` enum to strategy implementation:
- `EQUAL` -> `EqualSplitStrategy`
- `PERCENTAGE` -> `PercentageSplitStrategy`
- `EXACT` -> `ExactSplitStrategy`
- `HYBRID` -> `HybridSplitStrategy`
- `HIERARCHICAL` -> `HierarchicalSplitStrategy`

#### TaxCalculator
Calculates tax and service fees for each share:
- **Simple mode:** `tax = baseAmount * taxRate`, `serviceFee = baseAmount * serviceFeeRate`
- **Compound mode:** `tax = (baseAmount + serviceFee) * taxRate`
- Returns `taxAmount` (tax + serviceFee combined)

#### RemainderDistributor
Distributes penny-level remainders across participants:
- Calculates `remainder = totalAmount - sum(allocatedShares)`
- Distributes 1 unit (0.0001) per participant until remainder = 0
- Ensures all shares sum exactly to the total amount

#### ShareResult
Output of split calculation:
- `String userId`
- `BigDecimal baseAmount` (pre-tax)
- `BigDecimal taxAmount`
- `BigDecimal totalAmount` (base + tax)

### 8.2 Saga Orchestrators

#### SettlementSagaOrchestrator (7 steps)
1. **Validate** - Verify share data (userId, amounts, settlement status)
2. **Convert Currency** - If payer pays in different currency, call currency-service for conversion
3. **Debit Payer** - Call wallet-service to debit payer's account
4. **Credit Payee** - Call wallet-service to credit payee's account
5. **Create Settlement** - Persist Settlement record
6. **Mark Settled** - Call collection-service to mark share as settled
7. **Notify** - Publish RabbitMQ events (settlement.received to payee, settlement.confirmed to payer)

**Compensation (on failure):**
- Step 6 fails: unsettle the share
- Step 4 fails: reverse the credit (debit back from payee)
- Step 3 fails: reverse the debit (credit back to payer)
- Mark transaction as FAILED

#### NettingSagaOrchestrator (5 steps)
1. **Debit Net Payer** - Call wallet-service to debit the party who owes more
2. **Credit Net Payee** - Call wallet-service to credit the party who is owed more
3. **Mark Shares Settled** - Call collection-service to mark all netted shares as settled
4. **Create Settlements** - Persist Settlement records for each netted share
5. **Complete** - Mark transaction as COMPLETED

**Compensation (on failure):**
- Unsettle all shares
- Reverse wallet credit/debit operations

### 8.3 Service Implementation (TransactionServiceImpl)

#### settleShare(SettleRequest, userId)
1. Generate idempotency key: `SETTLE:{shareId}:{userId}`
2. Check for existing transaction with same key -> return existing if found
3. **[Feign]** Call collection-service to get share details
4. Validate: share exists, belongs to correct expense, user is the payer
5. Create Transaction entity (PENDING, SETTLEMENT type)
6. Delegate to `SettlementSagaOrchestrator`
7. Return `SettlementResponse`

### 9.2 Data Initialization
`DataInitializer` (implements `ApplicationRunner`) seeds 3 currencies on first startup:
- MYR (Malaysian Ringgit, "RM")
- SGD (Singapore Dollar, "S$")
- USD (US Dollar, "$")

### 9.3 Exchange Rate Resolution (3-tier fallback)

```
1. Redis Cache (key: "exchange_rate:USD", TTL: configurable minutes)
   |-- HIT: return cached rates
   |-- MISS: go to step 2
   
2. External API (openexchangerates.org)
   |-- SUCCESS: persist to DB, cache in Redis, return
   |-- FAILURE: go to step 3

3. Database (latest stored rates)
   |-- FOUND: return
   |-- EMPTY: use hardcoded defaults (USD=1, MYR=4.47, SGD=1.34)
```

### 9.4 Cross-Rate Derivation (Triangulation)
All rates are stored relative to USD. Cross-rates are calculated:
```
Rate(FROM -> TO) = Rate(TO/USD) / Rate(FROM/USD)
```
Example: MYR -> SGD = SGD_rate / MYR_rate = 1.34 / 4.47 = 0.299776

### 9.5 Service Implementation (ExchangeRateServiceImpl)

#### getAllRates()
Returns all supported currency rates relative to USD from cache/API/DB.

#### getRate(from, to)
1. Validate both currencies are supported -> throws `BadRequestException`
2. If same currency, return rate = 1.0
3. Fetch USD-based rates from cache/API/DB
4. Derive cross-rate via triangulation
5. Return `ExchangeRateResponse`

#### convert(from, to, amount)
1. Validate amount > 0 -> throws `BadRequestException`
2. Get rate via `getRate()`
3. Calculate: `convertedAmount = amount * rate` (scale=4, HALF_UP)
4. Return `ConversionResponse`
